## 07｜公共层与基类

**屏幕内容**

- core：帧标识、数据类型、最新帧槽和简单工具
- 功能层：相机、离线、Stereo、SDK 调用、点云与指标

**讲解**

## 10｜参数怎样找到代码

**屏幕内容**

- config.json 的字段 → 同目录 adapter.py
- adapter 输出 → 本次运行目录的 ROS 参数 / SDK profile
- 应用代码或 backend 算法读取最终参数
- parameter_map.json 记录字段、落点和限制

**讲解**

演示可以从 detection.score_threshold 开始：适配器修改实际 inference profile，模型后处理读取该阈值。融合里的 det_score_min 则是在点云语义融合时再次筛选检测结果，两者不是同一个阶段。参数索引帮助定位，但参数是否生效仍要看生成配置和对应运行输出。

**源码与阅读位置：** `parameter_map.json`。

## 11｜配置的四条规则

**屏幕内容**

- 所有相对路径以主 pipeline.json 所在目录为根
- null 继承 SDK；空字符串是否关闭由具体字段决定
- 环境变量先 export；未知字段和不支持的值立即报错
- 配置在启动时加载，当前不支持运行中热更新

**讲解**

visualization.save_root 为空表示不保存逐帧结果和 PLY；metrics 仍可写在 run-dir。不要把这个约定推广到每个字段。分割 align_corners 和 argmax_mode 在当前 SDK 固定为 true/bilinear，配置只允许继承或明确写这个契约，其他值拒绝。

**源码与阅读位置：** `features/segmentation/config.json`。

## 12｜输入模式与视差来源

**屏幕内容**

| 输入模式 | original_q8 | raft_stereo |
| --- | --- | --- |
| camera | SDK 左图 + 原视差 | SDK 同次采集左右图 |
| ros | 左图 + Q8 + 内参 | 左右图 + 双目内参 |
| offline | 单图不能恢复原视差 | 校正后左右图 + 内参 |
| recording | 回放录制的原 Q8 | 回放同一份左右图 |

**讲解**

模式切换由配置显式表达。原 Q8 与新 Stereo 应在同一份左右图和 Q8 录制上做对比，避免现场画面变化。offline 的图片格式可以是常见压缩图片或者固定大小的原始 YUV；完整点云链路需要符合双目几何约定。

**源码与阅读位置：** `features/offline/config.json`。

## 13｜相机直取流程

**屏幕内容**

- camera.json 定位厂商 .so 与相机 .cfg
- 同一次 SDK 采集读取左右图 / Q8 和矫正后内参
- 新 Stereo 自动选择左右图模式；原算法选择 Q8 模式
- 采集线程提交最新帧，处理线程执行推理和输出

**讲解**

相机适配使用真实厂商 SDK 的 ABI。新 Stereo 不能从左右目不同采集时刻拼图。取图的 timeout 与 retry_interval 是采集控制参数，不是模型推理耗时。当前环境验证了 ABI fixture 与线程退出，实际 X5 相机仍需要板端验证。

**源码与阅读位置：** `features/camera/src/mo_camera.cpp`。

## 14｜ROS 相机与算法节点

**屏幕内容**

| 发送方 | 消息 | 接收方 |
| --- | --- | --- |
| raw_camera_node | 左 / 右 sensor_msgs/Image | perception_node |
| raw_camera_node | 左右 CameraInfo，同帧时间戳 | perception_node |
| raw_camera_node | 原 Q8 Image（原方法） | perception_node |
| perception_node | 结果、掩码、点云、地图、指标 | 订阅方 / 可视化工具 |

**讲解**

相机发布节点和算法节点是独立进程。算法节点 ros 模式不直接打开相机，因此 received_images=0 首先查发布节点、话题、ROS_DOMAIN_ID、网络和 QoS。ros2 topic info --verbose 中 Subscription count 为 0 时，不能通过模型参数来解决。

**源码与阅读位置：** `features/ros/src/raw_camera_node.cpp`。

## 15｜ROS 输入话题

**屏幕内容**

| 数据 | 默认话题 | 要求 |
| --- | --- | --- |
| 左图 / 右图 | /camera/rgbd_left_nv12<br>/camera/rgbd_right_nv12 | 同次采集，tight NV12 |
| 原视差 | /camera/disparity_q8 | 16 位小端 Q8.8 |
| 双目内参 | /stereo/left/camera_info<br>/stereo/right/camera_info | 与图像精确同时间戳 |

**讲解**

默认 reliability 是 best_effort，queue_capacity 为 4；它同时影响接收缓存和订阅深度。内部 raw_camera 节点按照约定发布。外部节点需要核对 Image 的编码、宽高、step、字节数和 endian，不能只看话题名称一样。

**源码与阅读位置：** `features/ros/config.json`。

## 16｜精确配对与内参

**屏幕内容**

- 按时间戳缓存图像、原视差和 CameraInfo
- 所需消息全部齐全才组装一帧，超出容量清理旧消息
- 新 Stereo 检查左右校正标识与投影矩阵约定
- 外部只发布一次静态 CameraInfo，当前不能直接配对

**讲解**

精确时间戳避免把不同帧的数据合在一起，但会提高对外部发布节点的要求。CameraInfo 的 P 矩阵给出焦距和基线约定；bxf 是像素焦距乘基线毫米。当前实现把静态内参也按同帧消息处理，今后可以设计带有效期的标定缓存，但要有明确身份和变更规则。

**源码与阅读位置：** `core/include/perception_ros_so_demo/latest_frame.hpp`。

## 17｜线程与最新帧策略

**屏幕内容**

- 采集 / 订阅负责收帧，工作线程负责同步处理
- 在线模式只保留一个待处理最新帧，旧待处理帧可被替换
- 离线模式施加背压，逐帧处理并保留顺序
- 统计接收、替换、处理数量，区分吞吐与帧覆盖率

**讲解**

LatestFrame 让在线延迟不随着输入积压无限增长，但它意味着不是每一帧都执行了推理。对比时不能把原算法和新算法分别接入实时相机，然后直接逐帧比较，因为它们可能处理了不同的帧。录制回放应检查完整覆盖、失败帧和保存范围。

**源码与阅读位置：** `core/include/perception_ros_so_demo/latest_frame.hpp`。

## 18｜离线图片的转换

**屏幕内容**

- PNG / JPEG / BMP 等先解码，再转成 NV12 或 I420
- 原始 YUV 必须满足 640×544、紧密排列和精确字节数
- 640×544 YUV420 = 522240 字节
- 双目点云须确认校正和内参；不允许隐式改变几何

**讲解**

offline.format 指转换后的 YUV 格式，不是让 PNG 文件被当成原始 NV12 读取。原始文件扩展名及字节检查用于防止把图像压缩文件误读成 raw。普通单图的 letterbox/stretch 不能代替双目校正，完整双目链路必须使用匹配的几何尺寸。

**源码与阅读位置：** `features/offline/src/offline_image.cpp`。

## 19｜一帧的调用链

**屏幕内容**

```text
输入 / 精确配对 / 标定检查
  ↓ pending 最新帧槽
PerceptionNode::process → Caller::process
  ↓ full SDK 的单帧调用
检测分割 ∥ 视差 → 点云 → 地面 / 语义 / 地图
  ↓ JSON、ROS 消息、PLY、metrics
```

**讲解**

ROS 节点不自己实现所有算法，它准备 psdk_frame_v1、传递同帧标定并调用共享 SDK。SDK 内部根据输入视差是否存在决定用原 Q8 或调用 disparity provider。返回结果之后由节点发布和保存。处理接口是同步单帧调用，但 SDK 内部有并行任务。

**源码与阅读位置：** `features/ros/src/node_process.cpp`。

## 20｜SDK 内部任务依赖

**屏幕内容**

- 检测 / 分割与视差可以从同一输入开始执行
- 点云依赖视差与相机几何，语义融合还依赖推理结果
- 坐标变换 → 地面划分 → 障碍 / 语义 / 栅格地图
- 外层 JSON 当前固定四个任务节点，尚非任意插件图

**讲解**

外层 input、disparity、perception、report 描述运行阶段。内层 full SDK 的图才描述具体算法依赖。当前检测和分割在共享后端里调度，不支持仅往外层 JSON 添加一个任意 feature 就自动接入 C++ 插件。文档把这种限制写清楚，后续可以再设计注册与接口机制。

**源码与阅读位置：** `backend/r36_sdk/full/graph.cpp`。

## 21｜检测、分割与融合阈值

**屏幕内容**

| 阶段 | 配置 | 作用 |
| --- | --- | --- |
| 检测器 | detection.score_threshold | 低分框在检测后处理时过滤 |
| 检测器 | nms_threshold / nms_top_k | 重叠抑制与保留上限 |
| 分割器 | segmentation.model | 每像素类别输出 |
| 语义融合 | fusion.labels.det_score_min | 映射点云时再次筛选检测框 |

**讲解**

不要因为参数名称相近就认为修改的是同一处。CPU 检测的模型输入归一化和输出布局在 cpu_profile 中；X5 走 Horizon runner。分割的 resize 与 argmax 契约当前固定，需要改 SDK 源码才能改变。检测与分割模型文件应与构建环境和预处理保持对应。

**源码与阅读位置：** `features/detection/config.json`。

## 22｜新 Stereo 的模型契约

**屏幕内容**

- 当前新模型：NCHW [1, 3, 352, 640]
- 张量轴顺序之外，还要检查模型图像类型 NV12
- 左右输入顺序、内存对齐、量化信息和输出类型都要匹配
- runner 读取真实模型元数据；不靠文件名猜输入

**讲解**

NCHW 并不意味着必须喂 RGB float。该 X5 模型使用图像 NV12 输入；Horizon tensor codec 根据数据类型和有效尺寸处理平面对齐。换模型时同时核对输出视差的意义、分辨率和缩放关系。运行时 HBRT 与模型编译工具版本警告仍需按板端工具链处理，目录重构不会消除该问题。

**源码与阅读位置：** `features/stereo/runner/src/tensor_codec.cpp`。

## 23｜Stereo 缩放与视差恢复

**屏幕内容**

- 校正后的 640×544 左右图显式缩放到 640×352
- 模型视差恢复到原相机图像尺寸
- 视差数值只乘横向比例 W原图 / W模型
- 恢复后使用原图内参生成点云，避免混用两套几何

**讲解**

视差是水平像素位移，纵向缩放不能拿来乘视差数值。当前模型宽度同为 640，因此横向数值比例是 1；高度恢复只改变采样位置。若换成不同宽度，必须验证水平比例。strict 模式要求输入与模型元数据一致，resize 模式必须显式选择。

**源码与阅读位置：** `features/stereo/src/stereo_provider.cpp`。

## 24｜视差到点云

**屏幕内容**

```text
d_px = q8 / 256
Z_mm = bxf / d_px
X_mm = (u − cx) × Z_mm / fx
Y_mm = (v − cy) × Z_mm / fy
相机坐标 → 外参变换 → 机器人坐标与融合
```

**讲解**

bxf=focal_px×baseline_mm，因此输出深度单位是毫米；PLY 会按契约输出米。必须检查有效视差、范围、采样和坐标轴。点云点数多并不必然更好，错误视差同样会产生大量错误点。CameraInfo 或离线内参必须与校正后的图像尺寸和像素坐标对应。

**源码与阅读位置：** `features/pointcloud/backend/src/mapping.cpp`。

## 25｜点云、地面与语义地图

**屏幕内容**

- sample_step 控制点云采样密度
- 外参决定相机点到机器人坐标的变换
- 地面算法使用高度、范围、种子和距离阈值
- 分割 / 检测标签加入点云，再生成障碍与栅格地图

**讲解**

地面与语义融合涉及多个坐标系和单位，这是修改时需要重点回归的部分。pointcloud 的 ground 参数与 fusion 的 labels/cluster/map 参数分开放置，避免一份巨大配置里混杂几何和语义。保存 camera、robot、ground、obstacle、semantic 点云有助于逐阶段定位差异。

**源码与阅读位置：** `features/fusion/backend/src/label_fusion.cpp`。

## 27｜PLY 可视化的比较方法

**屏幕内容**

- 使用相同帧、坐标系、相机视角、裁剪范围和点大小
- 依次看平面、边缘、空洞、离群点和远近深度
- 分阶段比较 camera / robot / ground / semantic 点云
- 视觉更平滑不等于真实精度更高；精度需要真值

**讲解**

如果只比较两张自动缩放截图，点云包围盒变化会制造视觉差异。建议固定观察姿态，先检查坐标与尺度，再评估空间结构。模型可能把边缘抹平，让图看起来更干净却丢失障碍。没有激光或标定真值时，应报告可视化现象和数值差异，不能宣称准确率提升。

**源码与阅读位置：** `compare/report_compare.py`。

## 29｜性能指标的含义

**屏幕内容**

| 指标 | 解释 | 比较时注意 |
| --- | --- | --- |
| 阶段耗时 | 预处理 / 推理 / 后处理 | 并行阶段不能简单求和 |
| graph / process / compute | 不同代码边界的墙钟耗时 | 先统一测量边界 |
| CPU / RSS | 进程资源与常驻内存 | CPU 可超过 100%，RSS 不是 BPU 内存 |
| FPS / 覆盖率 | 吞吐、输入和处理数量 | 丢帧后 FPS 不能代表完整处理 |

**讲解**

ROS 模式的算法进程统计不包含另一个相机发布进程。记录的原 Q8 已经生成，回放无法获得厂商内部原视差生成耗时。应分别报告公共后处理耗时和新 Stereo 的新增成本，不能拿回放原 Q8 的零生成时间当作算法快慢结论。

**源码与阅读位置：** `features/metrics/src/process_metrics.cpp`。

## 30｜同数据录制

**屏幕内容**

- 一次采集保存左图、右图、原 Q8.8 和真实标定
- manifest 记录帧号、时间戳、尺寸、格式和文件路径
- 模型、录制内容与配置计算 SHA256，避免数据被替换
- 两种视差算法回放同一份录制，不重复开相机采样

**讲解**

录制既能比较原视差与 Stereo，也能比较 v10 与模块化新版本。模型和标定身份和图像同样重要。录制目录应作为不可变测试资产，增加场景时建立新批次，而不是覆盖已有文件。数据包不包含模型和厂商 SDK，需要记录各自版本身份。

**源码与阅读位置：** `compare/capture_camera.cpp`。

## 31｜结构回归与算法差异

**屏幕内容**

| 目标 | 需要固定 | 合适的判断 |
| --- | --- | --- |
| 目录重构正确性 | 数据、模型、SDK、参数、坐标系 | 输出完全一致或明确容差 |
| 新逻辑的差异 | 数据与公共参数，记录变量 | 逐阶段数值和视觉差异 |
| 算法真实精度 | 数据、标定、真值与指标 | 对真值的误差，而非相互一致 |
| 性能结论 | 硬件、温度、并发、保存设置 | 预热后交替多轮运行 |

**讲解**

结构回归首先证明搬迁没有改变可观察行为。算法迭代允许输出不同，但每个差异应能对应预期修改。两套算法都输出同样错误时，彼此一致不能证明正确。性能实验建议 ABBA 顺序或交替重复，使用中位数和 p95，记录失败和丢帧。

**源码与阅读位置：** `docs/04_同数据验证方案.md`。

**屏幕内容**

## 38｜常见报错的排查顺序

**屏幕内容**

| 现象 | 先检查 | 再检查 |
| --- | --- | --- |
| Invalid sdk path | sdk_root 是否存在、包结构 | 真实架构与动态库依赖 |
| received_images=0 | 节点、话题、订阅数、Domain | QoS 与网络 |
| 有消息但不处理 | 时间戳、格式、内参是否齐全 | 标定、尺寸与队列 |
| PLY 尺度 / 形状异常 | 视差单位、bxf、外参、左右顺序 | 模型预处理与版本 |

**讲解**

先从输入和契约排查，再进入模型和算法。输出日志里 SO ready; no camera opened 对 ROS 输入是正常状态，表示等待外部数据。旧问题中只有 stereo_source 发布、订阅数为 0，说明算法节点未参与该通信环境，不能把它解释为 Stereo 推理卡住。

**源码与阅读位置：** `docs/03_新手阅读与开发.md`。

## 39｜当前设计中合理的部分

**屏幕内容**

- 共享一条下游链路，原 Q8 与新 Stereo 可共用融合
- 同帧校验、尺寸检查和显式缩放降低隐性几何错误
- 在线最新帧与离线背压分别满足不同目标
- 配置快照、逐帧输出和 PLY 支持定位与复现

**讲解**

这些设计仍需理解其适用条件。共享链路让比较更公平；精确配对让几何身份更明确；不同排队策略分别偏向在线低延迟和离线完整处理；结果快照让实验可追溯。保持这些优点时，也要继续记录失败帧和资源范围。

**源码与阅读位置：** `docs/02_代码逻辑合理性分析.md`。

## 40｜需要继续改进的部分

**屏幕内容**

- ROS 类虽已拆文件，仍同时拥有采集、配对、处理和输出状态
- 同步保存与指标 flush 会干扰在线尾延迟
- 分割固定契约、内部全帧锁和共享推理限制可扩展性
- 成功帧指标之外，还需统一失败、超时和丢帧统计

**讲解**

这是下一步的修改方向，本次没有为了重构目录顺带改变这些行为。建议首先提取明确的输入控制器和结果处理器，再考虑有界异步保存和端到端时延。内部 exact_frame_mutex 会影响多实例并发，需要测试后再改。所有改动都应通过固定录制和失败注入验证。

**源码与阅读位置：** `docs/02_代码逻辑合理性分析.md`。

## 41｜下一轮修改顺序

**屏幕内容**

- 第一步：补齐身份、失败、覆盖率和时延观测
- 第二步：抽出输入、处理、输出的职责接口
- 第三步：异步保存、静态标定缓存和可配置后处理
- 每步独立比较固定录制，保留结果与版本

**讲解**

修改顺序基于风险和可验证性：先看清行为，再调整职责，最后做可能改变输出或调度的优化。旧版和新版都要保存模型、标定、数据哈希。对于算法准确性，逐渐增加带真值的场景；对于性能，固定温度、资源和输出设置后交替重复。

**源码与阅读位置：** `docs/04_同数据验证方案.md`。
