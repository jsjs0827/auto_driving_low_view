# 分享讲稿：从双目图像到语义点云

> 版本说明：本文及原 42 页 PPT 为模块化 v1 的分享材料，保留当时的目录和验证背景。模块化 v2 的 scheduling / sdk 新布局、调用链及待改问题见 [07_调度层设计](07_调度层设计.md)，本轮实际验证见 [00_交付与验证](00_交付与验证.md)。


适合 45～60 分钟技术分享。建议讲解 40～45 分钟，留 10～15 分钟演示与问答。读者无需预先懂整个项目，但应知道图像和程序输入输出的基本概念。

本文件按 30 个主题组织备课，与实际 42 页 PPT 的逐页讲稿互补。每页写明核心结论、画面建议、屏幕内容和口头说明。演示结果必须使用真实运行目录，不应把测试 fixture 的点云当作 X5 新模型效果。

## 01｜从双目图像到语义点云

**核心结论：** 一个项目里统一输入、视差来源、原有感知融合和可复现验证。

**画面：** 左右图 → 视差 → 彩色点云 → 地面/障碍/语义地图。

**屏幕内容：** `perception-stereo-modular-v1`；相机 / ROS / 离线；原 Q8.8 / 新 Stereo；结构与开发方法。

**讲解：** 今天重点不只是介绍一个 Stereo 模型，而是解释数据怎样进入系统、怎样经过原有感知链路、结果如何输出，以及改代码后怎样知道没有改坏。文件目录已经重新整理，后面所有图都能对应到实际文件。

## 02｜这套系统做哪些事

**核心结论：** 检测、分割、视差和融合共同形成应用结果。

**画面：** 四张功能卡：目标框、像素 mask、3D cloud、语义/障碍栅格。

**屏幕内容：** 输入左图；双目或 Q8.8；检测/分割；点云/地面/融合；ROS/PLY/指标。

**讲解：** 检测告诉我们目标在哪，分割告诉我们每个像素属于哪类，视差提供几何深度。仅有检测或视差都不是最终地图。融合将这些结果映射到空间中，形成地面、障碍和最近障碍等应用信息。

## 03｜先划清实现与验证边界

**核心结论：** 源码可读、编译通过、板端效果验证是三个不同层次。

**画面：** 三层：应用适配 → r36 full SDK → 厂商 SDK/BPU。

**屏幕内容：** 默认 ROS 链接安装 SDK；项目带可重编 backend 源码；改 backend 要重编并切换 SDK；x86 不能代表 X5 BIN。

**讲解：** 项目已把真实算法源码按功能归档，但默认依然使用已安装 SDK 作为稳定基线。改 C++ 后端文件不会自动改掉板端的共享库。新模型的精度和性能必须在真实 X5 上验证，本地 CPU 和合成输入只能证明对应的软件通路。

## 04｜一帧的共同契约

**核心结论：** 同帧身份、格式、几何、所有权必须一起正确。

**画面：** 一个 FrameBundle 示意：ID/stamp、左图、右图/Q8、K/bxf、来源。

**屏幕内容：** 源 640×544；NV12/I420；Q8.8=像素视差×256；内参+bxf；拥有内存。

**讲解：** 几张图尺寸相同，不代表来自同一次采集。SDK buffer 还活着，也不代表释放后仍能使用。程序先确认身份和缓冲布局，再复制到自己的内存，才能交给异步 worker。点云异常时，先核对这一层，往往比直接怀疑模型更有效。

## 05｜为什么重新按功能组织

**核心结论：** 从参数能沿着映射找到实现，降低“到处找文件”的成本。

**画面：** root/global、core、features、backend、compare 五块目录图。

**屏幕内容：** 根：pipeline/camera/visualization；模块：config/adapter/include/src；backend：真实 SDK；compare：同数据验证。

**讲解：** 应用源文件不再都挤在 ROS 包的 src 里。ROS 包目录保留 CMake 和 package.xml，便于兼容构建。检测/分割共享推理管理，真实 C++ 放 inference backend；这比复制两份会话逻辑更清楚。

## 06｜全局配置只做少量决定

**核心结论：** 日常从 `pipeline.json` 开始。

**画面：** 展示短 JSON，突出 `input_mode` 与 `disparity_source`。

**屏幕内容：** camera/ros/offline/recording；original_q8/raft_stereo；sdk_root；其余参数下沉模块。

**讲解：** 全局配置不需要用户手写四段 DAG。前端根据输入和方法生成固定编排。根 camera.json 统一相机设置，visualization.json 统一发布、保存和坐标系。这样切模式时不用复制一整份大配置。

## 07｜功能参数从哪里改

**核心结论：** 只修改负责该功能的 `config.json`。

**画面：** 8 行参数地图。

**屏幕内容：** ROS 话题；offline 文件；Stereo 模型；det 阈值；seg 后处理；pointcloud 地面；fusion 聚类/地图；metrics。

**讲解：** 默认 null 表示继承原 SDK 参数，避免重排目录时悄悄改行为。检测置信度阈值与融合二次筛选阈值不是同一个阶段。所有相对用户路径都以主 pipeline 文件目录为根，不能按功能配置所在目录猜路径。

## 08｜配置怎样真正生效

**核心结论：** 原始 JSON 经校验和映射后才进入 C++/SDK。

**画面：** pipeline + feature JSON → configuration.py/adapter → 参数 YAML + full JSON + mapping JSON + profile → node/SDK。

**屏幕内容：** 类型/范围/未知字段校验；null 继承；本次运行目录；`--prepare-only`。

**讲解：** 只把字段写进 JSON，并不代表算法使用了它。adapter 必须映射到后端真正读取的字段。prepare-only 适合检查生效配置，它不打开相机，也不运行模型；因此配置准备成功不能写成算法测试成功。

## 09｜四种输入模式各自负责什么

**核心结论：** 三种运行输入，加一种可重复比较输入。

**画面：** camera、ROS、offline、recording 横向对比。

**屏幕内容：** camera：直取；ROS：订阅同帧；offline：已校正左右图；recording：左/右/原 Q8 同次录制。

**讲解：** 离线图片可以解码成相机处理格式，但颜色格式转换不会产生标定。新 Stereo 点云需要校正双目对。原 Q8.8 的同数据比较必须录制原视差；不能从单图编造一个原方法参照。

## 10｜相机 SDK 的资源与标定

**核心结论：** 读取同次捕获，复制后释放，内参来自 SDK 校正结果。

**画面：** open → set/readback mode → get RGBD → copy → release → close/restore。

**屏幕内容：** 模式 1 新 Stereo；模式 2 原 Q8；640×544/1280×1088 已知参考；fx/fy/cx/cy/bxf 缩放。

**讲解：** 新方法需要左右图，不必主动调用原视差计算。SDK 返回的相机参数要与校正图一致。源分辨率缩放时，水平焦距和 bxf 按水平比例变化；内参不是任选一套能跑起来的数值。退出时恢复相机原模式。

## 11｜ROS 节点与话题图

**核心结论：** 相机发布与算法订阅是两个角色。

**画面：** raw_camera → left/right/Q8/CameraInfo → perception → result/metrics/clouds/maps。

**屏幕内容：** 话题名字、类型、QoS、ROS domain；默认 `/perception_ros_so_demo`；同 stamp。

**讲解：** 看到 topic 不等于订阅匹配成功。出现 received_images=0 时，先看算法 node 是否真的活着，再看 endpoint 和 QoS。只看发布端输出了点云或图片，不能证明另一个算法节点消费到了它。

## 12｜为什么使用精确时间戳配对

**核心结论：** 为几何正确性拒绝混帧。

**画面：** 左 100、右 101 不能配；左/右/Info 100 完整后提交。

**屏幕内容：** ExactFrames；有界捕获缓存；stale/evicted 计数；CameraInfo 每帧同 stamp。

**讲解：** 模糊配对虽然能更容易出结果，但移动场景下点云可能错误。当前严格策略要求每帧内参消息也有相同时间戳，静态只发布一次的外部相机要增加适配。时钟回退会被当成旧帧，需要明确重建会话或 epoch 策略。

## 13｜线程与最新帧策略

**核心结论：** 在线保持新鲜，离线保持完整。

**画面：** capture/callback → 一个等待槽 → active worker → SDK 内部任务。

**屏幕内容：** 回调只校验配对；一个 active + 一个 pending；在线替换 pending；离线背压；CPU/RSS 有界。

**讲解：** 输入每秒 30 帧、计算只能每秒 5 帧时，无限队列会让机器人看到很久以前的画面。当前正在处理的帧不会取消，等待帧被最新完整帧替代。离线回归更关心每个文件是否都处理，所以使用背压。

## 14｜原 Q8 与新 Stereo 的接入点

**核心结论：** 两种视差进入同一后续融合链路。

**画面：** 原 Q8 → frame.disparity；左右图 → provider → SDK disparity task；汇入 mapping。

**屏幕内容：** 原方法提供 Q8；新方法注册左右对；新方法 `frame.disparity=nullptr`；provider 被实际调用才算成功。

**讲解：** SDK 优先使用已传入的视差。如果新方法还带着原 Q8，会绕过新 provider。当前代码清空这个字段，并检查 provider 是否真的被调用，防止“配置新方法，实际还跑原视差”。

## 15｜模型形状、图像类型与张量

**核心结论：** NCHW 不等于 RGB float。

**画面：** metadata 卡：双输入、NCHW [1,3,352,640]、NV12、单视差输出。

**屏幕内容：** runtime 查询；左右输入名；aligned size/stride；cache clean/invalidate；解码量化。

**讲解：** Horizon runner 按实际元数据确认输入类型、布局、对齐与输出量化，不修改张量属性假装兼容。如果模型不再是双输入单视差，或者输出单位变了，需要改契约和测试，而不是只改两个尺寸值。

## 16｜640×544 到 640×352 的几何

**核心结论：** 只在 Stereo 分支缩放，视差只按横向比例恢复。

**画面：** 源 640×544 → 模型 640×352 → 恢复 Q8 640×544；下方公式 `d_src=d_model×640/640`。

**屏幕内容：** 宽度倍率=1；不乘 544/352；检测/分割仍看源左图；源内参不改。

**讲解：** 视差定义为水平位移。高度恢复改变采样网格，不改变水平视差单位。把高度比例也乘上去，会把整幅深度拉错。即使几何倍率对了，模型对垂直变形后的纹理响应仍需要真实数据验证。

## 17｜SDK 内部真正的任务图

**核心结论：** 检测/分割与视差可并行，后续按依赖汇合。

**画面：** dnn 与 disparity 双支路，RGB/cloud/labels/transform/ground/maps 依赖图。

**屏幕内容：** `full/graph.cpp::steps`；worker_threads=2；禁用任务依赖展开；外层图不是调度器。

**讲解：** 外层 JSON 的四段只是产品编排。新 Stereo 在 SDK disparity task 内运行，并不是提前单独跑完的第二个进程。任务 trace 记录真实执行；并行任务时间之和不是整帧墙钟时间。

## 18｜检测与分割为何共享 inference

**核心结论：** 参数按功能分，公共模型会话与输入校准共用。

**画面：** common input pack → det pre/infer/post + seg pre/infer/post。

**屏幕内容：** detection/segmentation config；runner DetectEngine/SegEngine；固定 bilinear+align_corners；exact_frame_mutex。

**讲解：** 共享代码减少两套加载、内存和校准逻辑漂移。shared SDK 在 X5 和 CPU 都固定分割 bilinear+align_corners，不能只改 JSON 切换。后端还有进程共享工作空间，因此跨 pipeline 整帧加锁。拆文件不等于已支持多帧并行；后续要先显式拥有状态，再安全去锁。

## 19｜视差怎样变成点云

**核心结论：** 几何关系简单，但单位和无效值必须严格。

**画面：** 像素 u/v、双目基线、深度 Z；三条公式。

**屏幕内容：** `d=q8/256`；`Z_mm=bxf/d`；`X=(u-cx)Z/fx`；采样步长；无效 d 排除。

**讲解：** bxf 是像素焦距乘毫米基线，后续点云输出使用米制。这里最容易出现千倍单位错误或不同内参混用。先用已知距离平面验证比例，再看边缘或地面分类。sample_step 控制稀疏程度，也影响耗时和点数。

## 20｜地面、语义与地图融合

**核心结论：** 视差变化会经过分类阈值被放大成应用差异。

**画面：** camera cloud → labels → transform → Patchwork → grids；det/seg 结果输入 labels。

**屏幕内容：** 地面阈值；检测框深度筛选；mask/聚类；passable classes；地图分辨率与范围。

**讲解：** 少量视差噪声可能让平面变厚，接着产生地面缺口或伪障碍。因此应先比较相机点云，再看地面与融合。融合的检测分数阈值只是二次筛选，不能代替检测器阈值。改算法时保持其他参数一致才好归因。

## 21｜输出、坐标系与 PLY

**核心结论：** 结果保存与 ROS 发布分开控制。

**画面：** 一次结果 → result/mask/maps/cloud topics；另一路 → save_root/frame-id-stamp。

**屏幕内容：** camera/robot/ground/obstacle/semantic；save_root 空不保存 PLY；metrics.write_jsonl 只关指标文件；view 指针寿命。

**讲解：** 有 metrics 文件不代表有逐帧 PLY。visualization.json 决定逐帧保存，run-dir 记录配置与指标。相机坐标和机器人坐标不能混比。SDK view 是借用数据，异步保存必须先转成拥有内存的快照。

## 22｜一帧指标怎样解释

**核心结论：** 看墙钟、CPU、内存和覆盖率，不能只看 FPS。

**画面：** acquire → queue → compute → publish/save 的时间线；CPU/RSS 卡。

**屏幕内容：** compute/graph/stereo/save；det/seg 各阶段；CPU ms 与 %；RSS；paired/processed/dropped。

**讲解：** stereo_ms 包含转换、缩放、打包、推理和恢复，不是纯 BPU 时间。CPU 多线程累积可超过 100%。当前 metrics 在成功帧后生成，失败要另统计覆盖率，不能把失败难帧漏掉后宣称平均耗时更好。

## 23｜怎样公平比较性能

**核心结论：** 比较相同范围，记录预热、顺序和进程边界。

**画面：** A→B→B→A 时间线；compute 与 end-to-end 两条量尺。

**屏幕内容：** 固定硬件/温度/频率；warmup/repeat；同模式；保存影响单列；原 Q8 生成不可从回放测得。

**讲解：** 回放中原 Q8 已经录好，新 Stereo 却仍现场计算，所以两者差值不是完整系统的所有成本差。ROS 算法进程不包含独立相机进程 CPU，直取包含 SDK 线程。CPU 百分比下降也可能是墙钟时间增长造成，必须同时看 CPU ms/frame。

## 24｜一次录制，两条算法

**核心结论：** 一次采集的左/右/Q8 录制是效果 A/B 的基础。

**画面：** read-only recording → original / stereo 两个独立 runner → matched report。

**屏幕内容：** manifest + hashes + calibration；相同 det/seg/fusion；按捕获键配对；输出不可覆盖。

**讲解：** 分别跑两次相机，无法保证看到同一帧。当前录制工具保存同次捕获的数据和内参，比较 runner 共用后续 SDK。输入、模型和配置清单让我们能回到首次差异，而不是只能看最终截图。

## 25｜从 PLY 视觉比较走向定量验证

**核心结论：** 从最早产生差异的中间结果开始。

**画面：** input → disparity → camera cloud → ground/obstacle → fused map 的排查阶梯。

**屏幕内容：** 有效视差率/分位数；平面残差；同像素深度；ROI 分类比例；固定视角与抽样。

**讲解：** 两份 PLY 用同坐标、同视角、同裁剪、同颜色和点大小。完整点云做定量，预览抽样只服务显示。没有真值时，我们能说差异和稳定性，不能直接把原方法当绝对正确答案。

## 26｜结构回归与算法 A/B 分开

**核心结论：** 移目录期待等价，换模型允许差异。

**画面：** 左：v10 original vs modular original；右：modular original vs modular stereo。

**屏幕内容：** 同方法先对等；mask/Q8 byte 比；点云数值容差；旧对旧确定性；首个差异帧。

**讲解：** 如果同时改目录、阈值、模型和线程，很难知道问题来自哪里。先用原 Q8 把结构回归过了，再切新模型。PLY 文件哈希不等价于几何差异，因为文本格式和点顺序也会变化；需要理解格式后做数值比较。

## 27｜合理之处与待改之处

**核心结论：** 目录清楚后，仍要诚实面对耦合和验证空白。

**画面：** 保留：同帧/RAII/有界队列/同链路；改进：版本身份/ROS耦合/共享状态/同步I/O/失败统计。

**屏幕内容：** 不造空基类；core 放真实契约；问题列入 docs；先回归后优化。

**讲解：** 我们保留已有可靠的生命周期和同帧检查。当前 Node 类仍集中编排，检测分割后端仍大且共享状态，保存仍在 worker 中，配置也不是任意插件系统。这些是下一步清楚可验证的方向，不应靠移动文件就宣布解决。

## 28｜伙伴怎样开发一个新功能

**核心结论：** 参数→接口→实现→固定数据测试，形成最短闭环。

**画面：** 需求/单位 → config/adapter → code → prepare-only → golden recording → report。

**屏幕内容：** 默认继承旧行为；新参数校验；后端重编身份；同方法回归；保留差异案例。

**讲解：** 只调整阈值不必新建 C++ 类；暴露已有后端参数时，要确认真正读取的字段。改算法必须重编 SDK。真的新增第二家相机或第二类模型后端时，再抽 IFrameSource/Provider，并定义所有权、取消、错误和标定，不先制造继承树。

## 29｜构建与测试平台矩阵

**核心结论：** 每个平台证明的事情不同。

**画面：** Windows Python、WSL x86、AArch64 cross、X5 replay、X5 live 五行矩阵。

**屏幕内容：** 配置/报告；ROS+CPU；目标链接；真实 BIN；硬件采集/稳定性；编译命令入口。

## 常见问答备忘

**为什么不把所有东西都变成基类？** 当前共同点主要是数据契约，过早继承会掩盖不同输入的取消、标定和所有权差异。core 集中真实共享类型，第二个实现出现后再抽接口。

**换模型只改路径够吗？** 只有当双输入单视差契约、类型、量化和输出语义被 runner 支持时才够。当前尺寸可按元数据校验并显式 resize；不能靠改尺寸兼容任意模型。

**为什么已经能出 PLY，还要看视差？** 地面/融合会放大几何差异。先看最早产生问题的结果更容易定位根因。

**为什么 CPU 降了，算法却更慢？** CPU % 是 CPU 时间除以墙钟窗口，等待 BPU 或更长处理时间会改变分母。看 CPU ms/frame 和 compute_ms 才知道工作量与速度。

**能不能立即宣称新模型精度更好/更差？** 没有真值时只能比较结果差异、稳定性和应用表现。需要已知距离/标注或可信真值才能算绝对精度。

**配置能任意开关 feature 吗？** 目前能选择已有输入和视差来源，并修改已映射参数。检测/分割/融合组合受固定契约限制，任意插拔需要后续明确设计。

**改了 backend 为什么没效果？** 检查是否重编 SDK、运行时是否加载新安装目录、共享库哈希是否变化。
