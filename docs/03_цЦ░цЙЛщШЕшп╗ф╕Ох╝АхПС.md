# 新手阅读与开发：先跑一帧，再改一个功能

## 1. 先认识几个词

| 名称 | 本项目中的意思 |
|---|---|
| ROS 节点 | 一个参与 ROS 通信的程序。本项目有相机发布节点和算法节点 |
| Topic / 话题 | 节点间发送消息的通道，名字、类型和 QoS 都要匹配 |
| SDK | 厂商或项目提供的库。本项目同时用相机 SDK 和 full perception SDK |
| C ABI | 动态库对外的 C 调用约定。本项目用函数、句柄和版本化结构体交互，C++ 业务对象保留在内部 |
| 检测 | 在图像上找目标，输出类别、置信度、矩形框 |
| 分割 | 给每个像素赋类别，如草地、非草地、石板 |
| 视差 | 左右相机里同一物体的水平像素位移，通常近处大、远处小 |
| Q8.8 | 用 16 位整数表示视差，实际像素值为整数除以 256 |
| 点云 | 一组 3D 点，可以附带颜色、语义等字段 |
| 融合 | 结合几何、分割和检测，得到地面/障碍/语义和栅格地图 |
| DAG | 有向无环任务图，表示先后依赖及能并行执行的任务 |
| Task / 任务 | 图中的一个执行节点，依赖完成后才能开始；可顺序调用多个 Feature |
| Feature / 功能执行器 | 一个已注册的可执行计算包装；配置中的注册名必须对应真实代码 |
| Artifact / 产物 | 任务之间传递的带类型结果，例如图像、检测框、分割或点云 |
| Binding / 绑定 | 把产品图的某个节点连接到本帧真实要调用的函数 |
| Session / 会话 | 一次初始化后持有的模型、配置、工作空间和资源，通常跨多帧复用 |
| Provider | SDK 需要视差时调用的接口；新 Stereo 通过它接入 |
| Profile | SDK 的细节配置，前端会在本次运行目录里生成/覆盖所需部分 |

“模型是 NCHW”只说张量轴顺序，不说明该用 RGB float 还是 NV12 字节。当前新模型元数据为 NCHW `[1,3,352,640]`，图像类型为 NV12；真实 runner 会读取元数据再分配和打包。

## 2. 10 分钟建立代码地图

先记住这些入口：

```text
pipeline.json                     选择输入和视差方法
features/<功能>/config.json       修改该功能的参数
features/<功能>/adapter.py        看参数怎样映射到实际运行配置
features/<功能>/include、src      看接口、数据和应用端实现
features/<功能>/backend           看需要重新编译 SDK 才生效的算法实现
scheduling/config/               看配置如何编译与解析
scheduling/dag/                  看依赖图构建、校验与执行机制
scheduling/pipeline/             看产品怎样把功能绑定到每帧任务
scheduling/inference/            看检测/分割的内层任务编排
sdk/                             看公开接口与 SDK 构建入口
```

`src/perception_ros_so_demo/` 现在主要是构建入口。不要因为算法 C++ 已移动到功能目录，就误以为 ROS 的 package 名称也改变了。

检测目录包含真实的 `backend/include/percep_demo/detection_post.hpp` 和 `backend/src/detection_post.cpp`（IoU/NMS）；分割目录包含 `segmentation_post.hpp/.cpp`（基础 CHW argmax），以及当前实际使用的 `backend/include/seg_post.hpp`、`backend/src/seg_post.cpp` 和 `seg_post_reference.inc`（双线性工作空间与参考实现）。共享数值后端在 inference 功能，CPU 阶段在 `features/inference/cpu/`，输入校准/打包在 `features/inference/preprocess/`；任务图编排在 `scheduling/inference/`。这不表示两套推理引擎或每种会话状态已完全独立。融合接口 `MappingAlgorithms` 仍持有地面分类状态，修改前先阅读合理性分析。

更完整的目录和调用链见 [架构与目录](01_架构与目录.md)。

## 3. 日常到底改哪一份配置

全局入口 `pipeline.json` 的默认内容很短：

```json
{
  "schema_version": 2,
  "input_mode": "camera",
  "disparity_source": "raft_stereo",
  "sdk_root": "${SDK_ROOT}",
  "sdk_base_config": null
}
```

实际文件中的 `_help` 是说明字段，可以保留。想切换输入或方法，只修改这两个字段，保留其他设置：

| 想做什么 | `input_mode` | `disparity_source` | 还要改哪份文件 |
|---|---|---|---|
| 相机直取，新模型 | `camera` | `raft_stereo` | `camera.json`、Stereo 模块配置 |
| 相机直取，原 Q8.8 | `camera` | `original_q8` | `camera.json` 的 `auto` 会选择原模式 |
| ROS 左右图，新模型 | `ros` | `raft_stereo` | ROS 模块话题与内参确认 |
| ROS 左图+原 Q8.8 | `ros` | `original_q8` | ROS 模块的左图/Q8/内参话题 |
| 离线左右图，新模型 | `offline` | `raft_stereo` | 离线模块的左右文件和真实内参 |
| 同数据原/新对比 | `recording` | 任一已有方法 | 根配置的 `recording` 段，使用 `--both` 时两种都跑 |

普通单图不能恢复原相机 Q8.8。新 Stereo 离线点云需要一一对应的、已经校正的 640×544 左右图，不能把任意两张照片当作双目输入。

### 常见参数位置

| 要改什么 | 配置位置 | 实际作用代码 |
|---|---|---|
| 相机 `.so` / 厂商 `.cfg` | 根 `camera.json` | `features/camera/src/mo_camera.cpp::Camera::Impl::open` |
| 采集超时/重试 | 根 `camera.json` | 同上 `Camera::Impl::next` |
| ROS 左右图/Q8 话题 | `features/ros/config.json` | `features/ros/src/perception_node.cpp` 建订阅 |
| 精确配对缓存 | ROS `queue_capacity` | `ExactFrames` 的 capacity，同时影响订阅深度 |
| 离线图片/格式/频率 | `features/offline/config.json` | `node_input.cpp::configureOffline/sourceStep`、`offline_image.cpp::load` |
| Stereo 模型和尺寸 | `features/stereo/config.json` | `StereoProvider` → `HorizonStereoModel` |
| 检测模型/置信度/NMS | `features/detection/config.json` | `adapter.py` → 推理 profile → `DetectEngine` |
| 分割模型/后处理契约检查 | `features/segmentation/config.json` | 模型可换；X5/CPU 均固定 `true/bilinear`，其他后处理需改 SDK |
| 完整推理 profile / 内部 DAG | `features/inference/config.json` | null 继承 SDK；显式路径仍受 shared SDK 固定契约校验 |
| 点云采样、外参、地面阈值 | `features/pointcloud/config.json` | `MappingPipeline`、地面算法 |
| 语义筛选、聚类、地图大小 | `features/fusion/config.json` | `MappingAlgorithms`、地图渲染 |
| PLY 保存/发布/坐标系 | 根 `visualization.json` | `node_output.cpp`、`node_process.cpp`、`cloud_output.cpp` |
| CPU/RSS/FPS 指标频率 | `features/metrics/config.json` | `node_metrics.cpp`、`process_metrics.cpp` |

根 `parameter_map.json` 提供逐参数的 `config_file/json_path/adapter/effective_target/implementation(file,symbol,line)`，用于从参数快速跳到真实位置。代码移动后可运行 `python3 tools/generate_parameter_map.py` 更新。分割的 `align_corners`/`argmax_mode` 只允许 null 或固定的 true/bilinear；不要将它们理解为可自由选择的后处理选项。

`tools/run_pipeline.py` 是保留命令的薄入口；真正用户配置编译在 `scheduling/config/python/configuration.py`，启动实现位于 `scheduling/launch/python/run_pipeline.py`。C++ 的 full 配置解析在 `scheduling/config/src/full_config.cpp`，内层任务 profile 解析也在该层。沿着“功能 adapter → 生效文件字段 → C++ 读取符号”查，比搜索全项目所有同名 JSON 更直接。

地面后处理仍有未开放的内部常量，例如 `ground_dist=0.05` 和滤波参数，它们不受 Patchwork 的同名近似阈值控制。另外 `ground.enabled:false` 关闭分类后，ground/obstacle cloud 会留空，不会自动改成“全部点都是障碍”。这类行为及后续方向见 [代码逻辑合理性分析](02_代码逻辑合理性分析.md)。

阈值有两个不同阶段：`detection.score_threshold` 决定检测器输出哪些框；`fusion.labels.det_score_min` 是融合时再次筛选检测结果。改后者不能替代前者。

### 四条简单配置规则

1. `null` 表示继承 SDK 现有值，不是 0、空字符串或关闭；不要随手把所有 null 换成示例数值。
2. 所有用户相对路径统一相对**主 `pipeline.json` 所在目录**，不是相对功能 JSON 所在目录。
3. `${SDK_ROOT}`、`${DET_MODEL}` 等环境变量要先设置；找不到模型/库会在启动前失败。
4. 未支持的字段会被拒绝，尤其不能自行加入检测/分割 `enabled`；配置会在启动时生效，当前不支持运行中热更新。

`pipeline.json` 可通过 `features` 引用另一组功能配置，也可用 `camera_config`、`visualization_config` 指定统一文件。这适合保留实验配置；引用中的相对路径仍以主文件为根。复制一份主文件到项目外时，需要一起调整这些引用，不能指望原目录隐式被找到。

## 5. 结果在哪里

逐帧结果另由根 `visualization.json` 控制：

## 6. 按一帧调用链阅读源代码

### 第一步：程序入口

`features/ros/src/main.cpp` 初始化 ROS，创建 `PerceptionNode`，执行 executor。`perception_node.cpp` 声明参数、创建 SDK engine、订阅/发布话题、启动 worker，退出时关闭资源。

阅读时先找构造函数里 `input_mode`、`disparity_source`、`mapping_` 的设置，再找 engine 打开的地方，最后找 capture/worker 线程启动处。

### 第二步：找到输入从哪里来

`node_input.cpp` 包含相机读取、离线读取和 ROS 配对的连接逻辑。相机细节在 `features/camera/`，图片解码在 `features/offline/`。ROS 回调不直接跑模型，而是把同帧内容装成等待任务。

`ExactFrames` 把不同话题按时间戳拼成完整帧；`LatestFrame` 控制计算线程最多等一帧。两个类负责不同事情：一个解决“图像是不是同一帧”，另一个解决“计算来不来得及”。

### 第三步：找到模型和 SDK

`node_process.cpp::processFrame` 校验输入、填写 `psdk_full_frame`。原方法附带 Q8.8；新方法给 provider 设置左右图，让 SDK 回调产生 Q8.8。随后只调用一次 `Caller::process`。

`Caller` 是所有权包装，不是算法实现。下一步读 `sdk/src/` 的薄 C ABI 转发，再读 `scheduling/pipeline/src/full_pipeline.cpp` 的会话和当帧业务绑定；full 图在 `scheduling/dag/src/full_graph.cpp`，通用图在 `scheduling/dag/src/task_graph.cpp`。检测/分割内层编排在 `scheduling/inference/`，数值算法在各 `features/` 功能中。调度决定顺序与所有权，功能完成具体计算。

### 第四步：找到输出

`node_output.cpp` 构造 ROS JSON、mask、地图和点云消息；`cloud_output.cpp` 处理 PointCloud2 和 PLY。`node_metrics.cpp` 组合性能字段，`process_metrics.cpp` 读 Linux 进程 CPU/RSS。

SDK view 中指针的寿命依赖 `Result`。发布当前代码会复制消息数据；不要把裸指针保存到下一帧或交给延迟线程。

想增加独立任务时，先阅读 [调度层设计](07_调度层设计.md) 中的注册名、参数 schema、产物键、依赖和独占资源规则。现有 full 图的候选节点仍由代码固定，不能只在用户 JSON 加一个名字便自动运行新功能。

## 7. 三种常见开发任务

### 任务 A：只调整一个阈值

例如调整检测置信度：

1. 修改 `features/detection/config.json` 的 `score_threshold`。
2. 执行 `--prepare-only`，打开本次生成的推理 profile，确认实际值已变化。
3. 用 5～10 帧固定录制集测试；检测框数可能变化，原 Q8.8、内参和输入哈希应不变。
4. 查看变化框和融合结果；不要只看平均 FPS。

不需要为每个阈值复制一个 C++ 类，也不应修改 SDK 安装目录里的稳定原文件。

### 任务 B：增加一个可配置参数

例如某个融合参数在后端已经存在，但前端尚未暴露：

1. 先确认后端真实读取位置、单位、范围和是否只在初始化读取。
2. 在对应 `config.json` 加一个简单字段，默认 `null` 继承，补中文 `_help`。
3. 在 `adapter.py::configure` 校验类型/范围并映射到正确后端字段。
4. 增加参数映射与一个有意义的配置测试：默认继承、显式覆盖、错误值拒绝。
5. 检查 `--prepare-only` 的生效文件，再用固定输入验证行为。

不要只加 JSON 字段却未映射；也不要写入一个与真实推理无关的同名副本。

### 任务 C：替换或改写算法

例如修改地面算法：

1. 从 `features/pointcloud/backend/src/ground_segmentation.cpp` 和 mapping 调用点阅读。
2. 保留旧实现或清楚的版本分支，保持输入输出契约和单位。
3. 重编 backend SDK 安装到新目录，前端与运行时指向这份 SDK。
4. 先同方法检查检测、分割、视差不变，再比较地面分类和下游融合。
5. 为首个差异帧保存输入和中间结果，补自动回归。

新模型只要仍符合 runner 支持的双输入/单视差输出契约，通常改 `features/stereo/config.json` 和模型路径即可；如果输入名字、张量类型、量化或输出语义变了，应修改 runner/codec 并测试，不能只改宽高强行运行。

## 8. 开发测试分几层

| 层 | 适合验证什么 | 不代表什么 |
|---|---|---|
| Windows Python | JSON 校验、参数映射、报告、文件身份和版本比较 | 不代表 Linux 相机/BPU 已运行 |
| WSL/Linux x86 | C++ 编译、ROS 通信、CPU ONNX、队列、错误/生命周期 | 不代表 X5 BIN 数值和板端性能 |
| AArch64 交叉编译 | 目标 ABI、头文件/符号、真实依赖链接 | 不代表硬件运行成功 |
| X5 固定录制回放 | BIN 输入契约、同帧输出、效果、计算开销 | 不包含已录制原视差的生成开销 |
| X5 在线相机/ROS | 采集、配对、丢帧、时延、长期资源和退出 | 独立两次采集不等于同数据精度对比 |

常用 Python 检查在项目根运行：

```bash
python3 -m unittest discover -s validation -p 'test_*config*.py'
python3 -m unittest discover -s validation -p '*compare*.py'
```

具体本版本检查命令和结果以 [交付与验证](00_交付与验证.md) 为准。已有 native SDK 与 ROS 环境时，`tools/build_native.sh` 会配置、构建、运行注册的 CTest 并安装；要明确设置 Linux native SDK，不能把 AArch64 SDK 给 x86 链接。

最重要的测试方法见 [同数据验证方案](04_同数据验证方案.md)：结构回归和算法 A/B 分开，先验证身份和数值，再比较性能。

## 9. 遇到问题按这个顺序查

| 现象 | 优先检查 |
|---|---|
| `Invalid sdk path` | `SDK_ROOT` 是否为包含 config/include/lib 的安装前缀，不是源码目录 |
| 模型候选不唯一 | 显式设置三份模型环境变量，核对实际路径和哈希 |
| `received_images=0` | 算法节点是否在运行、topic/subscription、ROS domain、类型、QoS |
| 收到图但没有 paired | 左右/Q8/CameraInfo 是否同 stamp，缺哪一类输入，缓存是否被淘汰 |
| 报原始 YUV 长度错误 | RAW 格式、尺寸和紧密字节数；PNG 应由图片解码通路读取，不是按 raw 解释 |
| 新 Stereo 报尺寸不同 | 源几何与模型尺寸分开；`image_transform` 是否显式 resize；实际模型元数据 |
| 有 PLY 但点云异常 | 左右顺序、校正、内参/bxf 单位、输出视差单位、外参、再看模型和融合 |
| PLY 没保存 | `visualization.save_root` 是否为空，保存频率与目录，是否是本次 run-dir |
| CPU % 降了但变慢 | 同时看 CPU ms/frame、墙钟时间、等待/I/O、进程范围 |
| 改 backend 没效果 | 是否重编了 SDK，实际加载的是哪一个 `.so`，哈希是否改变 |

停止优先用 Ctrl+C，让程序恢复相机模式并释放资源。强制 kill 只是异常退出手段；之后应确认厂商 SDK/相机是否需要恢复，不能把它当作常规停机流程。
