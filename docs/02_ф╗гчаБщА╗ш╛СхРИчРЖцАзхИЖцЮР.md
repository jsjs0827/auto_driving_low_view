# 代码逻辑合理性分析与后续修改方向

本文评审当前实现，不把“文件重新分类”当成“算法问题已经解决”。证据分为三类：**已从代码确认的行为**、**在特定使用条件下才出现的限制**、**需要真实 X5 数据才能确认的风险**。最后一类不能写成已经发现的模型错误。

## 1. 本次调整的合理范围

v1 已把应用端按输入、推理、融合、输出和性能分类。v2 将原 SDK 主要实现继续移出：用户/内部配置解析在 `scheduling/config/`，构图和验证在 `scheduling/dag/`，运行接口在 `scheduling/runtime/`，full 业务绑定与推理编排在 `scheduling/pipeline/`、`scheduling/inference/`。具体 CPU/预处理/相机/输出/统计/时序实现按功能归位；公开 C 接口在 `sdk/`，历史材料在 `archive/r36_sdk/`。

默认应用构建继续连接指定的已安装 SDK，方便保留基线。**本轮内部调度重构必须重编 `sdk/CMakeLists.txt` 并切换 SDK_ROOT 后才能验证。**仅构建前端或运行旧 SDK 不代表新内部实现通过；开发者必须区分“修改了文件”和“运行时确实加载了该实现”。

本轮明确增加了“调度决定依赖与生命周期，功能完成数值计算，SDK 维护对外 ABI”的边界。这是责任归位，不是已经消除所有状态耦合。完整设计和新增功能路径见 [调度层设计](07_调度层设计.md)。

## 2. 当前值得保留的设计

| 设计 | 为什么合理 | 代码证据 |
|---|---|---|
| 同次捕获身份优先 | 左右图、Q8.8 和内参混帧会生成看似合理的错误点云；严格匹配能尽早阻断 | `core/.../latest_frame.hpp::ExactFrames`；`features/camera/.../raw_capture.hpp` |
| 图像数据先拥有再释放 vendor buffer | 相机 SDK 释放后，worker 仍可能计算；复制为自有内存保证生命周期 | `features/camera/src/mo_camera.cpp::rgbd/gdc`、`core/.../capture_types.hpp` |
| 一个 SDK engine 一次处理一帧 | 后端有会话状态和共享工作空间，多帧同时进入同一 engine 风险高 | `features/ros/src/node_process.cpp::workerLoop` |
| 在线等待队列有界 | 输入快于推理时不会不断堆积延迟和内存 | `LatestFrame::put/take`，等待槽最多一帧 |
| 离线背压 | 测试时不应为了实时新鲜度跳过文件 | `node_input.cpp::sourceStep` 的 pending 检查 |
| 原/新视差共用后续链路 | 有利于把变化归因到视差，而不是混入另一套融合参数 | `scheduling/pipeline/src/full_pipeline.cpp` 统一 disparity→mapping；`StereoProvider` 仅提供 Q8.8 |
| 新模型真实元数据校验 | NCHW 形状并不能决定实际图像字节布局；输入类型、步长和量化必须看 runtime 元数据 | `features/stereo/runner/src/horizon_stereo.cpp`、`tensor_codec.cpp` |
| 模型仅创建一次 | 避免每帧加载模型的开销与资源泄漏 | `StereoProvider::Impl` 持有 `HorizonStereoModel` |
| C ABI 处捕获异常 | C++ 异常不跨越 C 回调边界，错误含 feature/task/frame | `StereoProvider::Impl::invoke noexcept` |
| RAII 拥有 SDK 结果 | 结果 view 是借用指针，发布复制完成后才释放 | `features/sdk_bridge/.../sdk_caller.hpp::Result` |
| 停止顺序明确 | 停采集、关闭队列、join、关相机、销毁 engine；provider 生命周期覆盖 SDK | `PerceptionNode::close` 和成员声明顺序 |
| 配置 null 继承 | 不因整理文件而把原 SDK 阈值悄悄替换为另一组默认值 | `scheduling/config/python/configuration.py::apply_features` 和各 `adapter.py` |
| 运行目录不可覆盖 | 配置和结果可以溯源，保留失败案例 | `tools/run_pipeline.py`、`compare/run_compare.py` |
| 性能口径显式输出 | task 并行时不能简单相加；CPU/RSS/FPS 各有不同含义 | `node_metrics.cpp`、`compare/report.py` |

## 3. 已确认的结构和逻辑限制

### 本轮搬迁后仍需要进一步拆分的代码

| 位置 | 保留的耦合 | 下一步方向 |
|---|---|---|
| `scheduling/dag/src/task_graph.cpp` | ArtifactStore、FeatureRegistry、构图校验、旧 CFG 读取、线程池及执行仍在一个文件 | 按 artifact/registry/validation/executor 拆文件，保持已有失败/关闭语义 |
| `scheduling/pipeline/builtin/runtime_features.cpp` | 具体 AI/点云/融合 Feature 包装与通用 Engine 会话实现仍同文件 | 把各功能注册器下沉到 features，Engine 只留 run/close/结果导出 |
| `scheduling/pipeline/src/full_pipeline.cpp` | 会话、当帧业务绑定、保存/JSON 和结果寿命仍集中 | 拆 Session、FrameResultBuilder 和 OutputWriter，先固定依赖和所有权 |
| `scheduling/config/` 与 `scheduling/inference/` | 主 parser 已归 config，但 `inference_session.cpp::loadOriginal` 仍随会话解析/校验原推理 profile；Python/C++ 也各有规则 | 把纯 profile 解析逐步抽到 config，明确schema/version；不让C++直接重读所有用户JSON |
| `features/camera/src/` 与 `features/camera/backend/` | 应用与旧 SDK 的两套相机封装仍存在 | 先统一捕获数据/错误/关闭契约，再决定是否共用适配层 |

把这些文件挪到独立层后，其问题更容易定位；本轮仍保留函数体和运行契约，未同时改写为任意图插件系统。

### A. 源码位置与运行时 SDK 位置容易混淆

**现状：** ROS 前端经 `find_package(perception_full_shared_sdk)` 和 `sdk_root` 使用安装目录里的 SDK。`features/*/backend/` 是可构建源码，修改它不会自动更新板端 `.so`。

**影响：** 开发者可能改了 `mapping.cpp`，却仍运行旧 SDK，然后误以为改动无效；也可能只替换 `.so` 而未记录版本，导致对比不可复现。

**下一步：** 在启动信息和 `run.json` 中记录实际加载的共享库路径、哈希、构建 ID 和 backend 源版本；给“基线 SDK”与“开发 SDK”各一个明确安装目录。构建脚本检查头文件与库是否来自同一安装前缀。不要直接覆盖稳定 SDK。

**证据：** ROS 包 CMake 的 `find_package`；`sdk_bridge::Caller::open`；全局 `sdk_root`。

### B. 外层 DAG 仍是固定编排，不是任意可插拔图

**现状：** 外层为 input/disparity/perception/report 四段；新配置用简单的 `input_mode`、`disparity_source` 自动生成该图。检测、分割、mapping、label fusion 当前按产品固定组合逐帧执行，回充及历史差分关闭。

**影响：** JSON 可以选已有方法和参数，但不能凭空增加一个 feature，也不能只添加 `enabled:false` 就任意关闭检测/分割。文件夹名是责任分类，不等同于插件注册机制。

**下一步：** 先列出真正需要的组合和依赖，再建立受约束的功能开关；每个开关定义结果缺省值、下游行为和错误策略。通用图编辑应排在真实需求之后，避免一开始暴露任意依赖形成无效配置。

**证据：** `tools/configuration.py::compile_pipeline`；`tools/run_pipeline.py::validate_dag`；`scheduling/dag/src/full_graph.cpp::steps`。

### C. ROS Node 拆成多个源文件后，职责仍集中在一个类

**现状：** `PerceptionNode` 仍持有配置、相机、同步器、队列、SDK、输出与统计。拆文件提升查找效率，但没有消除所有成员间依赖。完整工作帧 `Pending` 仍含 ROS 消息指针。

**影响：** 非 ROS 的相同算法回归仍需要另一条 runner；难以直接用纯 C++ 帧对象复用整套 worker。

**下一步：** 在稳定回归保护下，抽出真正与 ROS 无关的 `FrameBundle` 和 `PipelineSession`。ROS、相机、文件输入都转换为它；发布和保存消费同一结果接口。这里需要明确所有权和时间戳，不建议先造一组空基类。

**证据：** `features/ros/include/.../perception_node.hpp::Pending/PerceptionNode`；`compare/runner/src/main.cpp`。

### D. 检测/分割实现较大且共享全局工作空间约束

**现状：** 检测 IoU/NMS、分割基础 CHW argmax 已按功能拆出真实头/源且函数体不变；当前使用的双线性 `SegPostWorkspace` 与参考实现也完整移入分割目录。模型会话、预处理、张量读取与整体后处理入口仍在共享 runner；`dag_pipeline.cpp` 的 `exact_frame_mutex` 跨 Pipeline 实例串行化整帧，注释说明保留的数值辅助器存在进程共享工作空间和校准策略。

**影响：** 同一进程创建两个 pipeline 不代表可并行推理两帧；贸然去锁会造成数值或内存安全问题。单个源文件内同时修改检测和分割也增加回归面。

**下一步：** 先把隐式共享状态改为显式 session/lane 所有权，再拆 detector/segmenter 的输入与输出契约；独立验证后才评估跨帧并行。保留一个公共 BPU 会话/张量工具层，避免复制模型加载与 cache 管理。

**证据：** `scheduling/inference/src/dag_pipeline.cpp::exact_frame_mutex`；`runner.cpp::DetectEngine/SegEngine`。

### E. 在线与离线的调度目标不同

**现状：** 在线 latest-frame 允许替换等待帧；离线采用背压。两个独立在线进程即便看同一个场景，最终完成的帧集合也可能不同。

**影响：** 直接把两个在线输出按行配对，会把场景变化和丢帧差异当作算法差异。

**下一步：** 以一次采集的只读 recording 作为效果比较入口；在线只比较时延、丢帧、稳定性。若需要在线影子测试，从同一完整帧分发到两个隔离 session，并用捕获键匹配，另记录两条支路覆盖率与资源竞争。

**证据：** `core/.../latest_frame.hpp::LatestFrame::put`；`node_input.cpp::sourceStep`。

### F. 成功帧性能样本会漏掉失败代价

**现状：** `processFrame` 在 SDK 失败或 view 失败时报告错误并返回；metrics 在成功结果后生成。比较报告也明确只将非 warmup 的成功行用于性能统计。

**影响：** 一个版本失败了很多难帧，但成功帧变快，可能出现“平均耗时更好”的误导。

**下一步：** 同时输出 attempted/succeeded/failed/dropped 和错误类别；失败帧也保留端到端耗时。性能报告单独写成功覆盖率，并用相同捕获键的交集统计耗时，同时展示被排除帧。

**证据：** `features/ros/src/node_process.cpp::processFrame`；`compare/report.py::_success`。

### G. 保存、PLY 转换与 metrics flush 在处理线程里

**现状：** SDK 结果保存、PLY 写文件与 metrics 逐行 flush 都在处理路径执行。

**影响：** 慢存储会拉长 worker 时间、降低在线 FPS 并增加等待帧替换；这与纯推理速度不是同一件事。

**下一步：** 先把 save_ms 与 compute_ms 分开报告；必要时使用有界输出队列和专用保存线程。保存线程必须接管拥有内存的结果快照，不能把 SDK 借用 view 扔到后台后提前释放。队列满的策略和保存缺口也要记录。

**证据：** `node_process.cpp` 保存逻辑；`node_metrics.cpp` 的文件 flush；`sdk_bridge::Result` view 生命周期。

### H. 字符串 JSON 的类型约束较弱

**现状：** ROS 结果和 metrics 采用 `std_msgs/String` 的 JSON，字段拼接在输出代码中。

**影响：** 下游发现字段拼写或 schema 变化较晚，编译器不会检查订阅方类型；字段增加容易使示例和解析器不同步。

**下一步：** 给 JSON 增加稳定 schema_version 和契约测试；对长期机器通信考虑自定义 ROS message。可保留 JSON 作为可读审计结果，避免为简单诊断输出引入过重消息体系。

**证据：** `features/ros/src/node_output.cpp`、`node_metrics.cpp`。

### I. 仍有算法常量未配置化，部分开关语义需要补清

**现状：** 地面后处理里仍有硬编码，例如平面补点距离 `ground_dist=0.05`、降采样 `0.04`、半径滤波 `0.1/10`、统计滤波 `20/1.0`。它们不等同于 pointcloud JSON 的 Patchwork `th_dist` 等参数。关闭 `ground.enabled` 后，`beginFrame` 清空的 ground/obstacle cloud 不再被地面任务填充；程序没有自动把全部点归为障碍的替代策略。

**影响：** 调整一个 JSON 阈值不一定影响所有相似阶段；关闭地面分类也不等于保留完整几何地图。最终 maps 仍可能包含语义分支，但 ground/obstacle 的几何贡献会改变。

**下一步：** 把真正要调的后处理参数以单位明确的名字暴露，默认值保持原常量；为开关定义输出语义和测试，不替用户猜测关闭后的 fallback。参数地图只列当前已开放参数，不能声称已覆盖全部内部常量。

**证据：** `features/pointcloud/backend/src/ground_segmentation.cpp::runGroundSegmentation`；`mapping.cpp::beginFrame/ground/maps`。

### J. 点云与融合的状态边界仍有耦合

**现状：** `MappingAlgorithms` 的真实头文件已经归入融合模块，但类同时保存语义融合配置、Patchwork 实例、ground/no_ground/obstacle 点云和上一帧语义点云。地面分类的实现归点云目录，状态仍由同一内部类拥有。

**影响：** 目录分类比原来清楚，但不能据此认为两个模块已经可以分别创建和独立运行。只移动声明不会自动改变对象所有权；直接拆状态可能影响每帧清理和历史数据生命周期。

**下一步：** 先用同帧回归保护现有行为，再分别定义 `GroundState` 与 `FusionState` 的创建、清空及依赖；让 MappingPipeline 显式组合两者。暂时保留共享内部类比复制一份状态更稳妥。

**证据：** `features/fusion/backend/include/mapping_algorithms.hpp::MappingAlgorithms`；`features/pointcloud/backend/src/ground_segmentation.cpp`；`features/fusion/backend/src/label_fusion.cpp`。

## 4. 特定接入条件下的限制

| 条件 | 当前限制 | 建议处理 |
|---|---|---|
| 外部相机 CameraInfo 只发布一次 | exact 同步需要每帧同 stamp 的左右 CameraInfo，不会自动沿用静态信息 | 在适配节点按每帧附带已确认的内参；后续可实现有版本的静态标定缓存，需显式策略 |
| 相机时钟/ROS 仿真时间重置 | `ExactFrames` 认为 `stamp <= last` 是陈旧消息 | 重启会话，或设计显式时钟 epoch 重置，不要静默把接收时间替换进去 |
| 原始 PNG/JPEG 不来自校正相机 | 转成 NV12 只能改变编码，不能补出双目标定或正确视差 | 新 Stereo 离线必须使用已校正左右对与对应内参 |
| 640×544 以外的源几何 | 当前应用输入和映射契约固定该尺寸 | 改尺寸要一起改标定、图像布局、模型适配和回归集，不能只放宽一条 if |
| 没有原 Q8.8 录制 | 无法重放同帧原视差 | 用 SDK 同时录制左右图和 Q8.8；不能从左图编造原结果 |
| 关闭 ground.enabled | 地面/障碍 cloud 留空，不自动把全点云作为障碍；语义分支可继续进入地图 | 仅在了解此语义时关闭；后续补可选择的替代策略及测试 |
| ROS 与直取比较 CPU | ROS 相机进程不计入算法节点 CPU，直取相机线程计入 | 用同模式比较，或对两个 ROS 进程合计统计 |
| Windows 原生运行 | 当前相机 SDK loader 和 `/proc` 指标依赖 Linux，X5 BPU 模型也不是 Windows CPU 模型 | 用 WSL/Linux 做配置与 x86 功能验证；真实 BIN 用 X5 |
| 改分割后处理 | shared SDK 在 X5/CPU 均强制 `align_corners=true`、`argmax_mode=bilinear`，runner 自身能接收其他值不等于 SDK 支持 | 目前只允许 null 或固定值作为契约检查；其他值拒绝。改实现并重编 SDK 后再开放 |

这些限制在指定场景下存在，并不意味着当前默认 X5 相机配置无法工作。

另一个容易误解的配置是 `features/metrics/config.json` 的 `write_jsonl`：它仅控制是否写指标文件，真实节点仍发布 `~/metrics`；`every_n` 控制话题和文件采样间隔。不能把它当作“关闭整个性能功能”的开关。

## 5. 需要真实 X5 验证的风险

### 模型与 HBRT 版本告警

已有板端日志显示模型编译版本与 HBRT 运行版本不同。输入尺寸适配解决的是尺寸和布局问题，不会消除运行时版本差异。应使用匹配工具链重新导出模型或验证匹配运行库，比较同一批输入的输出，才能判断告警是否影响当前结果。

### 新 Stereo 的异常视差/地面效果

前一批实际数据中，新分支出现更多地面缺口与伪障碍。可能涉及模型、训练分布、预处理、量化、运行时或后处理；不能仅根据 PLY 断定具体根因。先检查源输入与张量、视差平台/极值、原始浮点输出和 Q8.8 转换，再向后检查几何与融合。

### 插值恢复与颜色转换

Stereo 分支通过 BGR 接口进入模型，可能发生 NV12→BGR→模型输入转换。源左图未被修改，但转换和插值本身需要用模型导出时一致的策略验证。当前垂直 resize 不改变水平视差倍率，仍可能影响模型对纹理和边缘的响应。

### 时间戳时钟域与 TF

当前一致性检查关注“同次捕获”，相机时间戳未必等价于 Unix 时间。接入依赖系统时钟的 TF、定位或多传感器融合前，应确认时钟域、偏差和同步机制，而不是只确认数值相等。

以上均是排查方向，不能写成已经证明的根因。

## 6. 建议的修改顺序

| 优先级 | 下一步 | 通过标准 |
|---|---|---|
| P0 | 固定同帧录制集、版本/模型/SDK 哈希、逐帧结果比较 | 结构回归可自动复现；首个差异能定位 |
| P0 | 补失败/缺帧覆盖率与真实加载库身份 | 失败不会被性能平均值掩盖 |
| P1 | 拆 ROS 无关的 FrameBundle/PipelineSession | 同一处理会话能由 ROS、相机、录制驱动 |
| P1 | 小步拆 detector/segmenter 状态和后处理 | 保持旧对旧一致，再移除隐式全局状态 |
| P1 | 把昂贵保存移出计算线程 | 输出内存有界、结果生命周期正确、保存缺口可见 |
| P2 | 静态标定版本与时钟 epoch 支持 | 不混用不同标定，不吞掉时钟回退 |
| P2 | 受约束的功能开关/typed ROS 输出 | 每种合法组合有契约和失败用例 |
| P2 | 多会话/多帧吞吐优化 | 不破坏数值一致性，板端真实收益大于额外内存/争用 |

先把结果可复现、可解释，再优化复杂并发。详细执行方法见 [同数据验证方案](04_同数据验证方案.md)。

## 7. 本文没有声称什么

v1 曾在真实 native CPU SDK 与 ROS 录制输入上完成结构回归，`validation/evidence/modular_v10_same_frame.json` 记录稳定检测/融合字段相同，包含 5 份 PLY、mask、Q8、map 等 27 个结果文件 SHA 一致。`modular_native_online.json` 覆盖错误时间戳拒绝、CameraInfo、相机 ABI fixture、等待帧替换和正常退出；fixture 不是实际相机硬件。`modular_ctest.log` 记录 v1 的 6 项 CTest 通过。**这些是保留的历史证据，不能代替本轮 v2 新 SDK 的构建和回放。**

v2 已另行完成新 SDK 31 项 CTest、ROS 应用 6 项 CTest，以及对 immutable v10 基线的两帧真实 CPU ONNX 回放；检测、mask、map 一致，五类 PLY 的最大 xyz 误差为 0 m，26 个二进制文件逐字节一致，详见 [v2 最终验证](../validation/evidence/v2_final_validation.json)。这覆盖本轮重编代码在指定回归输入上的行为，不扩大为所有场景或硬件的正确性证明。

这些检查不证明新模型更准确，也不证明 X5 性能提升；本地 x86/WSL 测试不能代替 BPU 模型板端验证；源码编译通过不能代替相机硬件测试。其余实际检查以 [交付与验证](00_交付与验证.md) 和 `validation/` 中本版本证据为准，旧版本的证据只说明对应历史版本。
