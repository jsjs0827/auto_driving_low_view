# V2 的线程预算与单实例启动

`engine.worker_threads` 仍表示每个 DAG 的工作线程上限。实际创建数量为“配置上限”和“启用任务数”的较小值，最少保留一个常驻工作线程；全部任务禁用的图也保留这个约定。禁用任务不会执行，报告中仍显示 `skipped`。执行依赖、事务提交、异常处理和 trace 字段不变。

例如：配置 16 个工作线程但只启用一个回充任务时，实际创建 1 个；启用两个任务时，实际创建 2 个。配置 1 个线程时仍使用独立常驻线程，并不在调用线程内执行。主地图图有多个启用任务，可能仍使用原配置数量，不能仅凭线程限额推断它会提速。

在线入口原本就采用“一个运行帧、最多一个待处理帧”的 latest 策略，等待帧被更新会计数；这是受控替换，不能直接当成相机采集错误。离线测试仍应逐帧处理完整数据。

为防止误启动多个完整感知进程，可显式使用应用启动脚本：

```bash
bash tools/run_single_instance.sh --resource x5-camera-main -- /absolute/path/to/application --config /absolute/path/to/pipeline.json
```

同一相机的所有启动者必须使用相同资源名和相同锁目录。默认锁目录为 `/tmp/perception-v2-single-instance-UID`，只协调同一用户、采用该脚本的程序。也可用 `--lock-dir` 指定当前用户所有、其他用户不可写的运行目录。资源名可使用英文字母、数字、点、下划线和连字符。

竞争时立即失败，退出码为 75，并由 `flock --verbose` 打印锁获取失败；不会结束已有进程。脚本使用 `exec flock --no-fork` 直接执行前台算法，Bash、flock 和最终算法沿用同一个 PID，没有单独等待算法退出的 flock 父进程。向这个 PID 发送 SIGTERM 或 SIGKILL 时，信号直接作用于算法；程序自己的正常退出码原样返回，所以被调用程序本身也可能返回 75。外部进程管理器应按信号终止解释退出状态，而不是期待固定的 shell 返回数值。

锁的文件描述符有意传给算法，并可能被 fork/exec 的子孙进程继承。只有最后一份描述符关闭时，锁才会自动释放；若算法退出后仍有持有描述符的子孙进程，下一次启动仍会返回 75。这种延迟释放防止仍有工作进程时误启动第二份实例。算法应保持前台运行，不得自行守护化、主动解锁或关闭继承的锁描述符。需要完整清理子进程时，应由服务管理器管理整个进程组或 cgroup；这个脚本不增加杀进程或服务监督机制。锁文件保留，避免删除锁文件引入竞争。

要求 Bash、支持 `--no-fork/--verbose/--conflict-exit-code` 的 util-linux `flock` 及 GNU `stat`，板端缺少这些工具时应先补齐。正式部署需验证实际板端工具能力和服务停止方式。不同用户或不同文件系统/容器命名空间、不同资源名/锁目录、直接绕过脚本的启动仍可能不互相协调。

这个脚本需要显式调用，未加入 SDK 内部，不阻止绕过它启动的其他程序，也不限制整板所有 BPU 使用者。检测、分割与地图数值缓存的原有锁继续保留；本次没有改变模型、阈值、采样间隔或输出精度。

验证时先运行单个完整感知程序，再单独进行有界的额外负载实验。至少记录整帧 p50/p95/p99/max、CPU、RSS、线程和 FD 数，以及等待帧替换、同步淘汰和真实采集错误。算法计算与保存/摘要/报告开销应分别计时。
