r27：全速 RGBD、双模型上限与同帧三分支测试

采集修复更新：默认全速补丁为 full-sync，恢复两处同步队列保护。旧r27无需重新交叉编译，安装工具补丁及短测命令见 r27_capture_fix_zh.md。

本包基于已验证的 r26 ARM 校准修正版，仍使用原 DAG / Task / Feature 框架。保留原模型、检测 letterbox、分割直接缩放及原后处理、compact_direct 精确输入优化和分割加速。每次只运行一帧；没有 AI 双缓冲，没有 VSE / 融合 BIN 替换。本轮不包含 JSON 配置简化。

本机只能完成源码审查、Windows 编译和 mock 验证。本包尚未在你的 X5 执行，实际 FPS 由板端测试报告给出。

每组至少两轮，采用正序 / 反序降低顺序偏差。默认成功路径共28阶段；性能组300帧、预热30帧。性能组不保存图像或全量 mask 哈希，验证组的落盘开销不纳入 FPS。

SDK 去除 1:3 限制的范围

程序先检查板上原 SDK SHA256 和预期 AArch64 指令，随后只在新结果目录创建 sdk_copy/libMoGeneralSDK-full.so。去掉已知 modulo-3 筛帧，并同步调整公共帧号和按需查找键的 /3、*3 映射；保留左右同步检查、VSE 启动保护和帧释放。板上的原 SDK、相机配置和模型文件不改写。 不支持的 SDK 哈希直接报错。

这只取消 SDK 软件筛帧，不能改变传感器自身帧率。新帧频率以 SDK 时间戳去重实测，不能按修改后公共 FrameId 连续就认定频率提升。

反汇编发现模式1存在 RGBD 左右色图交付、暂不计算视差的分支，详细证据在 validation/r27_sdk_mode1_static.json。每次模式1启动时，最多丢弃30帧，直到连续5帧左右图元数据有效且深度元数据全零，排空切换前旧队列；这不是AI双缓冲，也不计入FPS。排空不能证明缓存可用，随后真实按需请求仍必须成功；正式测量不跳过失败帧。静态证据不能代替板端能力探针。

Ubuntu 宿主机交叉编译

继续使用之前的 obs-v004-x5-build 容器名，从 Ubuntu 宿主机执行，无须进入容器，也无须拉取模型工具链镜像或重新编译模型。把源码包及其 .sha256 放在 /home/st/ini_code，执行：

cd /home/st/ini_code
sha256sum -c perception-x5-fullrate-parallel-r12-v27.tar.gz.sha256
tar -xzf perception-x5-fullrate-parallel-r12-v27.tar.gz
cd perception-x5-fullrate-parallel-r12-v27
sudo docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'
sudo bash tools/build_in_container.sh \
  --container obs-v004-x5-build \
  --sysroot /work/obs_v004_x5/sysroot_docker \
  --out /home/st/ini_code/r27_parallel_release

若实际运行容器名是 x5-build，只替换 --container 的值。不要填写镜像名称。直接执行 bash，不要 source 该脚本。

编译输出：

/home/st/ini_code/r27_parallel_release/perception-sdk-x5-r12-v27-fullrate-parallel.tar.gz
/home/st/ini_code/r27_parallel_release/perception-sdk-x5-r12-v27-fullrate-parallel.tar.gz.sha256

将这两个文件复制到 X5 /userdata/ai_infer_r12_v27/。

X5 解压和测试

先退出占用相机的旧程序，再执行：

cd /userdata/ai_infer_r12_v27
sha256sum -c perception-sdk-x5-r12-v27-fullrate-parallel.tar.gz.sha256
tar -xzf perception-sdk-x5-r12-v27-fullrate-parallel.tar.gz
cd perception-sdk-x5-r12-v27-fullrate-parallel
bash tools/run_parallel_x5.sh \
  --out /userdata/r12_v27_res \
  --sdk /app/data/metoak/lib/libMoGeneralSDK.so \
  --camera-config /app/data/metoak/demo/config/x5_camera.cfg \
  --det-model /userdata/ai_infer/data/mmyolo0828.bin \
  --seg-model /userdata/ai_infer/data/pidnet_0825_3classes.bin \
  --frames 300 --warmup 30 --capture-frames 10 \
  --verify-repeats 2 --rounds 2 --camera-retry-ms 1

模型仍是原板端 BIN；若实际路径不同，只改对应参数，不能换成 fused 模型。相机配置也应填写之前能出图的实际文件。若运行库定位需要额外路径，可重复添加 --camera-runtime-dir /实际/lib目录。

脚本有限帧运行，正常结束会关闭相机和卸载 SDK。先跑上述默认短测；需要每个性能阶段按时长测量时，额外加 --duration-seconds 60。该选项不是完整长测、相机重开或泄漏验收。

统计口径与配对边界

实际 FPS 按测量窗口内完成帧数 / 用时计算；新帧 FPS 按有效 SDK 时间戳去重。双模型固定回放可超过相机交付 FPS，在线处理不能据此推算已经达到同样速度。视差持续模式与同帧按需模式分别统计，不能混称为同帧三算法。

同帧三分支使用原引擎3个 worker：输入 Feature 后并行 detection / segmentation / disparity。所有分支完成才释放本帧结果、进入下一帧。ai_wall_ms截止检测、分割完成，graph_ms包含全部视差分支，在线 FPS包含取图及整张图完成。不能用相加各并行分支耗时解释总耗时。

检测和分割结果带当前输入帧号；视差 API只返回像素及尺寸，没有独立的输出帧号 / 时间戳。视差配对依据是当前帧公共 ID、已审计的 SDK 缓存查找及映射，元数据明确写 returned_frame_id_available=false。每帧请求必须成功；报告另列观测到三分支重叠的帧数及占比，至少一帧重叠不代表全部帧重叠。三区间重叠说明软件请求并发，不能证明三个 BPU 工作在硬件核心上同时执行。

CPU100%表示工作进程占用一个核心，包含 SDK 后台线程，不含 Python 采样进程；RSS是该进程，CMA是整板。短测不能证明没有泄漏。无标注集时，零差异是数值一致性，不是 mAP / mIoU 准确率。

Windows / Ubuntu 文件一致性

源包和交叉编译生成的 SDK均校验最终文件字节。源码、脚本、JSON、manifest全部UTF-8无BOM、LF；归档后再次逐项比对。Ubuntu / X5无需 dos2unix、重算manifest或手动修复源码。遇到校验失败请保留文件及报错，不要跳过校验。
