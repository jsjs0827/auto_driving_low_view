# r12-v24：最快精确路径＋按需视差，受控测试与重开资源定位

采用 r23 已通过同帧验收的 compact_direct 精确输入路径，显式接入按需视差，重点减少连续视差与检测、分割的资源竞争。本包提供完整源码、Ubuntu 宿主机交叉编译脚本、板端有界测试和报告生成器。本机 Windows 完成主机验证；实际 FPS、CPU、RSS、CMA 和视差延迟以新的 X5 数据为准。

## 保持的流程

| 环节 | r24 行为 |
| --- | --- |
| 检测输入 | 原图→原864×480 letterbox；1280×1088输入有效区564×480，左右各150；Y=127、UV=128 |
| 分割输入 | 原图直接缩放到832×480，保留实际 runner 的 Y/U/V 独立 FMA 校准和取整顺序 |
| 输入加速 | 紧凑 NEON 表、快速 I420→NV12 打包、补边缓存、直接写已有 BPU tensor；每帧 cache clean 保留 |
| 模型 | 原 mmyolo0828.bin 和 pidnet_0825_3classes.bin；不转换模型，不使用融合 BIN 替代 |
| 后处理 | 沿用已验证的原 CPU 兼容检测/分割实现，输出完整原图 mask |
| 调度 | batch=1，逐帧完成；同一帧检测与分割可并行；无跨帧双缓冲 |

本次不再改像素运算循环。先完成“原始实现→r21”“r21→compact_direct”的实际 BPU 输入零字节差、mask 零像素差和检测位级相等验收；失败立即停止性能测试，保存失败输入/输出。

## 新增内容

1. r21 与 compact_direct 在连续视差、按需不请求、每10帧请求、每30帧请求四种条件下各测两轮，第二轮完全反序。显式设置 SDK mode 并核对读回值。
2. 长测和重开固定使用 compact_direct＋按需视差，避免像 r23 一样只测试到自动选中的 r21。
3. 每次按需调用记录公开帧号、时间戳、返回码、尺寸、调用与复制延迟；校验请求次数、帧序号与尺寸。请求失败不算测试成功。
4. 模型/相机加载、预热、关闭、关闭后等待1秒、重开等边界保存 FD 目标/fdinfo、线程身份、maps、smaps_rollup、RSS/PSS 和整板 CMA。帧循环中不读取完整 maps/smaps。
5. 同进程重开比较“模型保留”“仅相机”，各自再比较两种关闭顺序。记录 SDK 关闭和卸载返回码；关闭失败时保留动态库并中止，避免卸载仍被 SDK 线程执行的代码。

## X5 解压与完整测试

将编译生成的两个 SDK 文件复制到 /userdata/ai_infer_r12_v24，然后执行：

```bash
mkdir -p /userdata/ai_infer_r12_v24
cd /userdata/ai_infer_r12_v24
sha256sum -c perception-sdk-x5-r12-v24-demand-resources.tar.gz.sha256
tar -xzf perception-sdk-x5-r12-v24-demand-resources.tar.gz
cd perception-sdk-x5-r12-v24-demand-resources

bash tools/run_x5.sh \
  --det-model /userdata/ai_infer/data/mmyolo0828.bin \
  --seg-model /userdata/ai_infer/data/pidnet_0825_3classes.bin \
  --sdk /app/data/metoak/lib/libMoGeneralSDK.so \
  --camera-config /app/data/metoak/demo/config/x5_camera.cfg \
  --sdk-policy full-sync --stream gdc --format i420 \
  --schedule free --variants r21,compact_direct \
  --frames 120 --warmup 20 --rounds 2 \
  --demand-intervals 10,30 \
  --long-seconds 600 --long-demand-every 10 \
  --reopen-count 10 --reopen-frames 20 \
  --reopen-camera-only 1 --close-policies restore,hold \
  --verify-save-every 10 --verify-visualize-every 0 \
  --resource-interval-ms 500 --settle-seconds 5 \
  --out /userdata/r12_v24_res
```

原相机程序应先退出。测试期间保持场景和板端负载。模型位置不同时只修改两个 --model 参数。full-sync 沿用已校验的独立 SDK 副本，不覆盖原 SDK 与配置。

默认31个阶段，包含600秒长测和四组各10次重开，完成或失败后退出，不会一直采集。预计约20～30分钟，取决于启停耗时。重开10次意味着11个相机周期。长测另有100000帧上限，提前达到上限会标记未完成。

## 对照矩阵

| 条件 | SDK mode | 视差请求 | 输入路径 |
| --- | --- | --- | --- |
| continuous | 2 | SDK连续计算，不额外调用按需接口 | r21、compact_direct |
| demand_idle | 1 | 不请求 | r21、compact_direct |
| demand_n10 | 1 | 每10个交付的测量帧一次 | r21、compact_direct |
| demand_n30 | 1 | 每30个交付的测量帧一次 | r21、compact_direct |

每组合两轮，共16个在线性能阶段；另有4个固定原图阶段隔离相机影响。mode=0 不是关闭视差，本轮在线矩阵明确使用1或2。

按需调用仍同步执行，保持单帧流程。间隔按交付帧计数，预热不请求；不是固定时间频率，也不是传感器帧率。demand_idle 仅用于观察无视差请求时的上限。最终方案应先满足业务需要的视差频率。

FPS 包含取帧、同步视差和轻量请求记录；wall_ms 是检测＋分割处理，不包含独立视差调用。必须一起评估 FPS、CPU、wall 与视差 P95。BPU API wait 包含执行、排队和竞争；同帧两条模型分支重叠，不能简单相加。

## 重开实验

- restore：保留 r23 行为，关闭前恢复打开时的原视差模式，再调用 moCloseCamera。
- hold：显式实验，保持当前按需模式直到 moCloseCamera，成功后才卸载 SDK。用于检查关闭前恢复连续视差是否影响残留，目前只是待验证假设。

两种顺序均分别测试模型保留与仅相机；每次关闭后观察1秒，重开后额外预热5帧。仅相机不加载检测/分割模型，也不执行推理或逐帧保存原图。

重开总 FPS 包含关闭、等待、打开、额外预热及边界诊断，不代表正常在线速度。closed_cycle_changes 和 settled_cycle_changes 比较可比关闭边界；最终关闭之前已释放模型，单独列出，不混入模型仍打开时的增长趋势。

FD 用目标、inode、mount 和数量比较，避免编号复用误判；线程用 ID＋启动时间。maps 变化是虚拟映射大小，smaps_rollup 是进程整体 RSS/PSS，不能据此给某个映射归因。快照有少量分配开销，应比较同一边界。整板 CMA 会受其他进程和异步释放影响，不能仅凭它断言 SDK 泄漏。不会强制关闭未知 FD。
